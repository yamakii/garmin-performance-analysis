# Analysis Standards

Consolidated reference for all analysis rules.

## 1. Data Access

- **MCP tools only**: `mcp__garmin-db__*` を使う。`.duckdb` への直接アクセスはしない。SQL は `query_db`（行をその場で返す。会話中の確かめ）か `export`（ファイル。Python での統計分析: PLAN → EXPORT → CODE → RESULT → INTERPRET）に書く。テーブルの場所は `get_db_catalog`
- **Token optimization**: `statistics_only=True` 優先。`get_splits_comprehensive()` で12フィールド一括取得
- **数値は当該テーブルから**: VO2max / LTHR / 体重 / HR ゾーン境界などの数値は、`athlete_profile.focus_notes` 等のプロフィール散文ではなく該当ツール（`get_vo2_max_data`、`get_lactate_threshold_data`、`get_body_composition_trend`、`get_heart_rate_zones_detail`）から取る。プロフィール記述は執筆時点のスナップショットで陳腐化する

## 2. Agent Rules

`/analyze-activity` が生成するセクションは **`run_note` の1つだけ**（run-note-analyst が担当）。数値・範囲判定・処方判定・シーン抽出は `get_run_report` が決定論的に算出済みで、run_note はそこに乗る散文（意味づけ・因果・流れ・重みづけ・次の一歩・再発と問い）のみを書く。共通ルール:

- **HR zones**: Garmin native zones のみ (計算式禁止)
- **文体**: 自然な日本語（体言止め回避）、コーチ的トーン、具体的数値。ポイントごとに所見と根拠だけを簡潔に書く

- **Grounding**: run_note の主張には REPORT 上の evidence キーを必ず付け、課題にできる条件は契約（`get_analysis_contract("run_note")`）とマージゲートに従う。範囲内・有利側のブレを弱点にしない

## 3. Coaching judgement（会話・スキル・run_note 共通）

**単一のランに成績はつけない**（星・点数・総合評価のいずれも出さない）。1本のランは REPORT の2つの問い（処方どおりだったか / いつもの自分と比べてどうか）で読む。

**コーチとしての見方を持つ**: ツールの判定を言い直して終えない（REPORT は走者も Web で見ている）。そのランや相談がこの走者の今（ブロックの流れ・週の負荷と回復・生活の事情・本人の判断・目標までの道のり）にとって何を意味するかを、自分の見方として話す。DB で確かめられることは確かめてから話し、データで決まらないことだけを決まらないと言う。

次の3つは答えの構成ではなく、間違えないための点検:

1. **目的**: このラン・プランは何のためか。目的自身の基準で読む。週・ブロック・目標にとっての位置は現在地（`get_current_standing`）で確かめる。検証は意味を支え、置き換えない
2. **事実**: データが示すことと、それが比較できるか（同じセンサー・同じ荷物・同じ基準。`comparability` / `provenance`）。主張はそれが決まる粒度で確かめ（ラン中の変化なら km ごと、平均で代えない）、ツールの注記（`reason`・参考値・`insufficient`）は数値と一緒に伝える。派生値をその入力の裏付けにしない
3. **適用条件**: ラベル（シーンの `kind` / `policy.verdict` / `flag_labels`）・ルール・過去の型（`retrospectives` / `focus_notes` の散文）を使う前に、その前提が今も成り立つかを `facts` や `export` の集計で確かめる。ラベルは入口であって結論ではなく、散文の言い換えは確認ではない

- **反論されたら**まず引用したデータを確かめ直し、データが変える部分だけを変える。丸ごと翻さず、根拠なく固執もしない
- **保守的なゲート**（カットバック・ACWR・症状・保護期間）は結論ではなく入力。抑える理由（`reason_ja`）を `gate_counterweight` と並べ、推奨は1つ。`cutback_due` を覆すのは記録されたオーナー決定だけ
- **走者専用のルール**は `get_coaching_rules(scopes=[...])` で読み、`rule_text` を指示として適用する（`rationale` は背景で引用しない）。リポジトリには書かない
- **走者が述べたランの事情**（荷物・通勤・歩いた理由など）は `get_activity_context` で読み、答えが出ていることを質問しない。会話で述べられたら確認を取らず `save_activity_context` で保存し「（記録しました: …）」の一行だけを添える。事情は原因の説明であって改善点ではない

### 改善提案

- run_note は契約の `next_challenge` を1つ書く（この制約は run_note だけのもの）。会話の締めを「次へ持ち越す1点」の型にしない。次のセッションの中身（距離・ペース・心拍帯）は週の処方と `/daily-checkin` が決めるので、1本のランからは名指ししない
- 数値は処方の値の引用だけ（心拍上限はガード表現）。処方に無い帯やペースを作らない
- 一般的助言禁止（「もっと練習しましょう」→ このランの所見に根ざした具体的な行動にする）
- **提案は維持目標であり今回の合否ではない**。目的を達したランには「成功条件」「失敗」の表現を使わず、「維持目標」「改善余地」として示す
## 4. Data Safety

- **data/ と result/ は git 未管理 — 削除したら復元不可能**
- 削除前: `ls -la` で中身確認 → ユーザーデータ有無判断 → ユーザー確認
- `rm -rf` をファイル有無未確認で実行禁止
- 誤配置ファイル → 正しいパスに移動してから削除

## 5. 過去の型を確かめるときの比較

- §3 の適用条件を確かめる比較は同じ基準で: 同じ暦期間か同じイベント前の同じ長さで並べ、基準を明示し、予定値は実績と分ける。週量平均だけでなく型が依存する条件（ロング本数・最長・直前の途切れ・レース後の伸び）を並べる
